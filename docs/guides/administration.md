# Администрирование

[К документации](../README.md) · [Работа с устройством](sessions.md)

В левом меню есть отдельная группа **Администрирование**: Сессии, Узлы, Профили устройств, Пользователи, Роли и права, Нагрузка и Журнал. Разделы видны пользователям с соответствующими правами. Эта группа отделена от общих разделов Сессии и Токены. Здесь управляют узлами, профилями устройств, доступом пользователей и смотрят историю работы.

## Роли и доступ

В разделе **Роли и права** создавайте роли с разрешениями на просмотр и конкретные действия. Назначение роли доступно кнопкой со щитом у пользователя. [Перечень прав и правила отзыва доступа](roles.md).

## Узел, агент и слот

| Название | Что означает |
| --- | --- |
| Сервер | Принимает вход пользователей, хранит настройки и распределяет сессии |
| Агент | Программа на машине, которая запускает устройства и передаёт экран |
| Узел | Эта машина в интерфейсе: её имя, ресурсы, доступность и занятые места |
| Слот | Место для одной сессии эмулятора на узле |
| Профиль | Docker-образ и параметры, с которыми создаётся устройство |

Раздел **Узлы** отвечает на вопрос «где можно запускать устройства»: здесь же подключают новые узлы и отзывают токен агента (в окне настроек узла).

Первый агент может подключаться через `BOOTSTRAP_AGENT_ID` и `AGENT_TOKEN` из конфигурации сервера. В списке он отмечен **Из конфигурации**. Для него не требуется отдельно создавать токен через интерфейс.

Список **Физические устройства** появляется, когда агент сообщает об Android-телефонах или планшетах, подключённых по USB. Колонка **Подключено к узлу** показывает машину, к которой подключён телефон. Слоты эмуляторов в этот список не входят.

## Подключить узел

1. Откройте **Администрирование → Узлы → Подключить узел**.
2. Задайте уникальный ID, IP узла и адрес сервера, доступный с машины агента. Понятное имя можно изменить в настройках узла после подключения.
3. Сохраните выданный токен и конфигурацию. Секрет показывается при выдаче; не отправляйте его пользователям фермы.
4. Скачайте пакет агента и запустите его на узле по [инструкции установки агента](../deployment/agent.md).
5. Дождитесь состояния **В сети**. Если подключение не произошло, проверьте адрес сервера, токен и журналы агента.

Не используйте один ID для двух одновременно работающих машин.

## Настроить узел

Нажмите карточку узла. В окне настроек находятся:

- имя, которое видят пользователи;
- IP и время последнего ответа агента;
- режим и количество слотов;
- лимиты CPU и памяти на слот;
- сведения о ресурсах, нагрузке и занятых сессиях.

В карточке ресурсы показаны парами «из общего»: занятые слоты, лимит CPU для запуска, доступная память и свободное место на диске. CPU — число логических процессоров, разрешённых для фермы, а не текущая загрузка. Если агент не передал значение, вместо него стоит «—».

### Состояния

Цвет заголовка карточки одинаков на обзоре и в разделе узлов: зелёный — в сети, серый — отключён администратором, красный — нет связи. Отключённый узел остаётся серым и после потери связи.

| Состояние | Что делать |
| --- | --- |
| В сети | Агент отвечает; новые сессии разрешены при наличии свободных слотов |
| Отключён | Новые сессии приостановлены администратором; для возврата нажмите **Включить узел** |
| Не в сети | Связь с агентом потеряна; проверьте процесс агента и соединение с сервером |

Кнопка **Отключить узел** подходит для планового обслуживания. Работающие сессии продолжаются. Если нужно остановить сам агент, сначала дождитесь освобождения слотов или завершите сессии из списка занятых мест.

**Отозвать токен** в разделе агентов — другое действие: оно лишает агент доступа к серверу. Для временной паузы используйте отключение узла.

### Выбрать число слотов

В ручном режиме задайте фиксированное количество мест. Например, для небольшого узла начните с двух слотов и проверьте нагрузку при одновременной работе устройств.

В автоматическом режиме сервис рассчитывает количество мест по CPU и памяти с резервом 20%; минимум одно ядро остаётся системе. В окне показан расчёт и ресурс, который ограничивает число слотов.

**CPU на один слот** и **Память на слот** также ограничивают выбор профилей. Профиль с лимитом контейнера 6 ГБ не поместится в слот с лимитом 4 ГБ. Редактор покажет такие профили до сохранения.

Уменьшение числа слотов не останавливает работающие устройства. Новые сессии станут доступны, когда число занятых мест опустится ниже лимита. Для автоматического расчёта нужен агент с поддержкой политики слотов; интерфейс подскажет, если его требуется обновить.

### Проверить нагрузку и владельцев

Раскройте **Диагностика узла**: здесь показаны загрузка CPU, занятая память, диск, GPU, версия и лимиты агента. Учитывайте время последнего замера. «Лимиты агента» — разрешённые ему CPU и память, а не текущий расход его процесса. Наличие GPU и доступность NVIDIA runtime — разные показатели: обнаруженная видеокарта ещё не означает, что контейнер может её использовать.

В **Занятых слотах** указаны профиль, владелец и состояние. Нажмите запись, чтобы перейти в сессию.

## Какие образы использовать

Профиль запускает готовый Docker-образ. Можно использовать опубликованный образ Google из [REGISTRY.MD](https://github.com/google/android-emulator-container-scripts/blob/master/REGISTRY.MD) или совместимый образ из своего registry. Первый профиль добавляется миграцией; новые профили создаёт администратор.

Пример ссылки на Docker-образ:

```text
registry.example.com/rdf-emulator:36.1-google_apis-x86_64@sha256:DIGEST
```

Здесь `30` — уровень Android API, а `30.1.2` — тег сборки образа. Это не номер версии Android. Указывайте полный тег, чтобы запуск не зависел от изменения `latest`.

При первом запуске агент скачивает отсутствующий образ. При следующих запусках использует локальную копию. Для этого сценария не нужно скачивать SDK-архивы или собирать образ на узле.

### Другие версии Android

Откройте **Профили устройств → Каталог образов**. Выберите узел-сборщик и registry, отметьте системные образы Google и нажмите **Собрать**. Задания сохраняются, проверяются загрузкой Android и публикуются по digest. Профили создаются автоматически в фоне даже при закрытом окне. ATD — отдельные облегчённые варианты для автотестов; для интерактивной работы обычно нужен стандартный образ. Очередь и активную сборку можно отменить. [Подробности](../deployment/registry.md).

## Создать понятный профиль

Откройте **Администрирование → Профили устройств → Профиль**. Адрес образа и `DIGEST` ниже условные: замените их данными своего проверенного образа. Пример параметров:

| Поле | Пример |
| --- | --- |
| ID профиля | `android-16-google-apis` |
| Название | `Android 16 · Google APIs` |
| Версия Android | `16` |
| Основной Docker-образ | `registry.example.com/rdf-emulator:36.1-google_apis-x86_64@sha256:DIGEST` |
| Тип устройства | Телефон / планшет |
| Состав Android | Google APIs |
| API-уровень | `36` |
| Архитектура / ABI | `x86_64` |
| CPU контейнера | `4` |
| Память контейнера | `6144` МБ |
| Ядра Android | `4` |
| Память Android | `4096` МБ |
| Внутренняя память по умолчанию / максимум | `16` / `32` ГБ |
| SD-карта по умолчанию / максимум | `1` / `4` ГБ |
| Параметры эмулятора | `-no-snapshot` |

Это стартовые лимиты, а не обещание производительности для любого приложения. После пробного запуска проверьте нагрузку узла и расход памяти.

### Чем отличаются параметры

**Контейнер** ограничивает процесс эмулятора целиком. **Android** задаёт ресурсы гостевой системы внутри него. Память Android входит в лимит контейнера; редактор требует оставить за её пределами минимум 1024 МБ.

Модель, разрешение, ABI и состав Android в разделе характеристик — описание для пользователя. Редактирование этих полей само по себе не меняет содержимое образа. Указывайте проверенные значения. Если характеристика неизвестна, оставьте поле пустым и проверьте фактические данные после запуска.

Ядра и память Android можно задать отдельными полями. Не дублируйте `-cores` и `-memory` в дополнительных параметрах.

### Размеры хранилища при запуске

- `diskGb` — размер внутреннего раздела по умолчанию, от 2 до 128 ГиБ.
- `diskMaxGb` — максимум, разрешённый пользователю; если не задан, равен `diskGb`.
- `sdcardGb` — SD-карта по умолчанию, от 1 до 32 ГиБ; пустое поле означает отсутствие карты.
- `sdcardMaxGb` — максимум SD-карты; если не задан, равен значению по умолчанию. Задайте его, чтобы пользователь мог включать или увеличивать карту.

Пользователь может уменьшить внутреннюю память до 2 ГиБ и отключить SD-карту. Увеличение возможно только до максимума профиля. Это размер хранилища внутри Android, а не квота всего контейнера на диске узла. Размеры передаются отдельными полями; `-partition-size` и `-sdcard` не нужно добавлять в аргументы.

### Переменные окружения контейнера

Поле `containerEnv` профиля предназначено для настроек, которые читает ваш Docker-образ. Их задаёт администратор, например `{"TZ":"Europe/Moscow"}`. Эти значения не заменяют параметры Docker и не добавляют mounts, devices или capabilities.

Разрешено до 16 переменных, значение каждой — строка до 512 символов без переводов строк и управляющих символов. Имена состоят из букв, цифр и `_`, начинаются с буквы или `_`. Служебные переменные (`ADBKEY_PUB`, `EMULATOR_PARAMS`, `AVD_CONFIG`, `PATH`, `HOME`, `USER`, `HOSTNAME`) и префиксы `NVIDIA_`, `LD_`, `DOCKER_`, `RDF_` зарезервированы фермой. Это настройки профиля, а не хранилище секретов; не помещайте сюда токены и пароли.

Отметьте **Рекомендовать для новых сессий**, чтобы профиль появился среди рекомендуемых. Отключение профиля убирает его из выбора для новых запусков; его можно включить снова.

### GPU в профиле

Создавайте один профиль для одной конфигурации Android. Пользователь включает **Ускорение GPU** при запуске. Ферма сама подключает GPU и настраивает графику.

В редакторе задаётся только **Поддержка GPU**:

- **CUDA** — NVIDIA GPU через NVIDIA Container Toolkit.
- **GPU** — графика через render node узла.
- **Не поддерживается** — запуск с программной графикой; переключатель ускорения заблокирован с объяснением.

Один основной образ и один лимит памяти используются с включённым и выключенным GPU. Выбирайте образ, который поддерживает оба режима. Дополнительных образов, лимитов памяти и GPU-флагов настраивать не требуется. Если совместимых узлов нет или GPU на них временно недоступен, причина показывается при запуске отдельно от поддержки самого профиля.

## Пользователи и доступ

В разделе **Пользователи** администратор управляет локальными учётными записями. Доступные операции зависят от выбранного режима входа. Пользователь может заполнить имя, фамилию, компанию и должность в своём профиле.

После удаления локальной учётной записи администратор может создать новую с тем же логином. Она получает новый ID, пароль и выбранную роль; настройки, доступы и история удалённого пользователя ей не передаются. Удалённые учётные записи LDAP и OIDC остаются заблокированными.

При LDAP/AD имя, фамилия, должность и компания читаются из атрибутов каталога. При OIDC используются соответствующие поля, которые передаёт провайдер входа. Эти значения обновляются при следующем входе; если поля пустые, проверьте, отдаёт ли их ваш провайдер. Пароль внешней учётной записи меняется у провайдера, а не в ферме.

API-токены находятся в отдельном разделе **Токены**. Личный токен действует с правами своего владельца. Системный токен предназначен для административной интеграции и даёт доступ к сессиям и настройкам сервиса. Выдавайте для обычного тестового скрипта личный токен с подходящим сроком.

## История, журнал и статистика

- **Сессии** — работающие устройства и действия над ними.
- **Нагрузка** — занятость слотов, число запусков и другая статистика использования.
- **Журнал** — история аренд, действия пользователей и администратора, сообщения сервиса.

После завершения сессии активная запись удаляется вместе с её доступами. В истории остаются сведения о том, кто, когда и на каком узле работал. История не восстанавливает устройство и его файлы.

Пользователь видит свою историю в профиле; администратор — общую. Для расследования проблемы сначала найдите сессию по владельцу и времени, затем сопоставьте её с действиями в журнале и логами агента.


### Отключить или удалить профиль

В **Администрирование → Профили устройств** зелёный заголовок карточки означает, что профиль включён, серый — отключён. Текстовое состояние указано под названием.

На карточке есть два отдельных действия:

- **Отключить** — запретить новые запуски; профиль остаётся в списке, его можно включить снова.
- **Удалить** — убрать профиль из каталога после подтверждения. История сессий сохраняется, Docker-образы на узлах остаются. Восстановления через интерфейс нет; ID удалённого профиля нельзя использовать повторно.

Если профиль занят, сначала завершите его активные сессии и отмените заявки в очереди. Ошибка удаления появится в общем уведомлении, а окно подтверждения останется открытым.

## Профили из JSON, секреты и опции Docker

Подробный формат и таблица совместимости образов — в разделе [Образы и профили](images.md).

- **Импорт и экспорт.** «Профили устройств → Импорт JSON»: сначала «Проверить», потом «Применить». Новые профили создаются выключенными; существующие меняются только с флагом «обновлять». «Экспорт» выгружает все профили, значения переменных заменены на `null`.
- **Переменные контейнера.** В редакторе профиля значения не показываются (вместо них `••••••••`): оставьте строку как есть, чтобы сохранить значение, или впишите новое. Значения шифруются (AES-256-GCM) ключом `SECRETS_KEY`.
- **Параметры Docker (JSON).** В редакторе есть отдельное поле для разрешённых опций: `shmSizeMb`, `ulimits`, `tmpfs`, `sysctls`, `command`, `entrypoint`, `emulatorParamsEnv`, `adbKeyEnv`, `farmFlags`. Привилегии, сеть хоста, устройства и тома задать нельзя.
- **Журнал.** Каждый импорт и обновление профиля через импорт пишутся в журнал действий (кто и какой профиль); содержимое файла и значения переменных в журнал не попадают.

## Разрешить изменение параметров запуска

В настройках запуска задаётся общее разрешение для обычных пользователей. В редакторе каждого профиля можно выбрать наследование, разрешение или запрет. Сервер повторяет проверку при создании сессии; скрытие полей в UI не является единственной защитой. Администратор может менять параметры независимо от пользовательского разрешения. GPU выбирается при запуске по возможностям узла.

## Пользователи и диагностика

Пользователи отсортированы по имени; карточка показывает логин, дату регистрации и роль администратора. Кнопки с иконками позволяют редактировать, сбрасывать пароль с генератором и удалять пользователя. Нельзя удалить себя или последнего администратора. Удаление сразу отзывает доступ, отменяет заявки в очереди и запускает остановку устройств. Слот освобождается только после подтверждённой очистки; при недоступном агенте остановка повторяется после восстановления связи. История сохраняется. Управляемый Keycloak/LDAP аккаунт при необходимости блокируется также у провайдера.

В общем **Журнале** доступны действия, поток логов приложения и диагностика сессии по её ID. Лог приложения получает события сервера, агента и эмулятора, подключение и отключение узлов, операции API, ошибки и медленные запросы. В строках указаны источник, код события, ID узла и сессии, когда они доступны. Успешный фоновый опрос не засоряет поток. Хранятся последние 2000 строк с момента запуска сервера; история процессов сессии сохраняется отдельно. Диагностика сохраняет процессы запуска/остановки, проверки ADB, состояние и вывод контейнера, включая неудавшиеся запуски. Вкладка **Логкат** внутри устройства предназначена для Android-приложений; следование за новыми строками можно остановить, шрифт — изменить.

## Управление образами

**Администрирование → Образы** объединяет registry, кэш узлов, политики хранения и историю очистки. При явном удалении связанные профили отключаются; их можно удалить вместе с образом. [Руководство](image-management.md). Права «Очистка registry и кэша узлов» и «Удаление образов с отключением профилей» выдаются отдельно в разделе ролей.
