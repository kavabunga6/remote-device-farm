# Сравнение WebSocket и WebRTC

В сессии откройте бейдж трансляции (`scrcpy` / `WebRTC`) и выберите транспорт.
Переключение переподключает браузер к тому же Android. Эмулятор не перезапускается.
WebSocket остаётся начальным режимом; ошибка WebRTC не маскируется автоматической подменой транспорта.

## Реализация

- Источник обоих вариантов — существующий scrcpy H.264. WebRTC пакетирует его в RTP без перекодирования и доставляет с узла в браузер по DTLS/SRTP. ICE может использовать TURN, если он настроен.
- Opus передаётся отдельной WebRTC аудиодорожкой. RTP clock считает реальные сэмплы из Opus TOC: неровные MediaCodec PTS эмулятора не превращаются в пропуски аудио. Пауза, перезапуск и фактически отброшенные пакеты сохраняют явные разрывы; старые данные не воспроизводятся задним числом. Если конкретный Android использует AAC или gRPC PCM, звук пока передаётся через WebSocket; бейдж явно показывает `Звук: WS`.
- Клавиши, текст и касания WebRTC проходят через упорядоченный надёжный DataChannel. События жестов сохраняют порядок отправки.
- Авторизация, проверка гостевого доступа и сигнализация остаются на сервере. Медиа и ввод имеют короткую возобновляемую аренду, связанную с авторизованным WebSocket; при его потере WebRTC закрывается, Android остаётся запущенным в пределах правил сессии.
- Видео WebRTC выводится в тот же canvas, поэтому снимки и запись браузера продолжают работать.
- При единственном зрителе WebRTC агент не отправляет дублирующий H.264/Opus через сервер. При смешанных зрителях доступны оба пути.

## Управление и восстановление

Управление привязано к поколению соединения и последовательности событий. Просроченные команды и повторы отклоняются на сервере и агенте, очередь ограничена, после потери управляющего клиента контакты отпускаются даже при наличии других зрителей. Подтверждение постановки команды не означает завершения её обработки Android.

Проверка связи браузера выполняется каждые 2 с, отсутствие ответов 8 с запускает восстановление. Последний зритель оставляет локальный scrcpy на 15 с для быстрого возврата; при разрыве агента с сервером льготный период 20 с. Эти интервалы не продлевают срок аренды Android.

## Включение на узле

WebRTC выключен по умолчанию. Нужны `AGENT_WEBRTC_ENABLED=1`, доступный браузеру IP в `AGENT_WEBRTC_HOST_IP` и опубликованный UDP диапазон 50000–50100 (переопределяется `AGENT_WEBRTC_PORT_MIN/MAX`).

Дополнительный файл `compose.webrtc.yaml` включает эти параметры для сервиса `agent`:

```sh
AGENT_WEBRTC_HOST_IP=192.0.2.20 docker compose --env-file .env.agent -f compose.agent.yaml -f compose.webrtc.yaml up -d agent
```

Для NAT и ограниченных сетей задайте `AGENT_WEBRTC_ICE_SERVERS` как JSON-массив стандартных RTCIceServer, например свой TURN. Параметры выдаются авторизованному зрителю; используйте ограниченные TURN-учётные данные. Без доступного ICE-маршрута WebRTC не подключится — выберите WebSocket. Прямое UDP-подключение и TURN проверяются для сети конкретной установки.

## Как сравнивать

В меню показаны фактический транспорт, RTT управления, число отрисованных кадров в секунду, а для WebRTC — RTT выбранного ICE-маршрута и потери RTP. RTT измеряет ответ канала и **не является задержкой нажатие → изменившийся экран**. На неподвижном экране scrcpy может не выпускать новые кадры; нулевой FPS сам по себе не означает обрыв.

Для корректного сравнения оставьте один и тот же профиль, разрешение, сцену и узел. Сначала WebSocket, затем WebRTC. Проверьте ввод, перетаскивание, звук, поворот 90°/180°, запись, отключение интернета внутри Android и краткий обрыв браузера. Старые нажатия после возврата сети не должны воспроизводиться.

Воспроизводимая локальная проверка: `node scripts/verify-webrtc.mjs`. Она соединяет настоящий Chromium с агентским WebRTC, кодирует/декодирует H.264, проверяет DataChannel, отбрасывание повторной и просроченной команды и отпускание контакта при закрытии. Числа из неё относятся к localhost, не к серверу и не к Android.

WebRTC поддерживает NACK и запрос свежего ключевого кадра. Короткие пачки сохраняются в ограниченных очередях: до 4 ожидающих видеокадров / 120 мс / 4 МиБ и до 8 аудиопакетов / 150 мс / 128 КиБ. Учитываются время в очереди и разница временных меток источника. Потеря зависимого видеокадра очищает цепочку до нового ключевого кадра; устаревшее аудио не накапливается. Полноценная адаптация битрейта кодировщика под полосу ещё не реализована; оба транспорта используют одинаковые параметры кодирования. TURN/TCP и сети с искусственными потерями требуют отдельного измерения перед выбором основного транспорта.
