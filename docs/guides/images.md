# Образы и профили

[Документация](../README.md) · [Установка registry](../deployment/registry.md)

Управление собранными версиями, удаление профилей вместе с образом и очистка кэша доступны в **Администрирование → Образы**. [Очистка и политики хранения](image-management.md).

## Готовые сторонние образы

> **Предупреждение.** Готовые Docker-образы эмуляторов, включая опубликованные разработчиками эмулятора, могут отключать аутентификацию ADB или игнорировать переданные ключи. Успешная загрузка Android, закреплённый digest и переменные `ADBKEY` / `ADBKEY_PUB` не подтверждают, что ключи проверяются.

Перед включением профиля проверьте ADB самого эмулятора: доверенный ключ должен подключаться, а независимый клиент с другим ключом — получать отказ. Проверку выполняйте в изолированной среде для каждого используемого digest, включая производные GPU-образы и адаптеры. Результат одной версии не распространяется на остальные образы.

Внешний ADB-прокси сервиса проверяет ключ пользователя отдельно; отказ этого прокси не подтверждает настройку ADB внутри образа. Не публикуйте напрямую порты ADB, gRPC и консоли эмулятора: доступ к ним должен проходить через механизмы авторизации сервиса. Образ, не прошедший проверку ADB, нельзя включать для выдачи сессий. [Результаты проверок](../verification.md).

## Создать профили

1. Откройте **Профили устройств → Каталог образов**.
2. Выберите узел-сборщик с Docker, KVM, свободной памятью и доступом к `dl.google.com`.
3. Укажите встроенный registry или registry компании. Адрес должен быть доступен Docker на каждом узле; для нескольких узлов нужен HTTPS и доверенная CA.
4. Выберите пакет Android. **ATD** — облегчённый вариант для автотестов; для работы с экраном выбирайте стандартный AOSP, Google APIs или Google Play.
5. Нажмите **Собрать**. Каталог показывает очередь, этапы и ошибки; сборку можно отменить. Сервер проверяет завершённые задания в фоне, поэтому окно можно закрыть.
6. После сборки, проверки загрузки/ADB и публикации по digest профили создаются автоматически. Проверьте ресурсы и включите нужные профили.

Один мобильный пакет может создать телефон и планшет с разными разрешениями. ТВ, Automotive и Wear используют свои SDK-пакеты. Каталог показывает реальные опубликованные пакеты, включая ABI и вариант системы.

Первая сборка скачивает несколько гигабайт. **Скачать на узлы** заранее прогревает включённые профили без занятия слота. Подробности, восстановление очереди и уборка registry: [руководство](../deployment/registry.md).

## Ресурсы и запуск

Лимит контейнера включает память Android и минимум 1024 МБ запаса для эмулятора. Пример: 2048 МБ Android и 4096 МБ на узле. CPU и память должны помещаться в лимиты слота.

Пользователь выбирает устройство в выпадающем списке. Пресетов нет. Изменение параметров запуска разрешает администратор: общее правило и переопределение конкретного профиля. Выбранные ресурсы проверяются сервером и агентом.

GPU выбирается **при запуске**, по возможностям узла: NVIDIA/CUDA или DRI. В профиле нет переключателя поддержки GPU. Драйвер и Container Toolkit устанавливаются на хосте; [настройка агента](../deployment/agent.md#gpu).

## Импорт и экспорт JSON

**Профили устройств → Импорт JSON** позволяет проверить файл до применения. Новые профили создаются выключенными. Обновление существующих ID включается явно; применение атомарно.

[Пример импорта](../examples/profiles-test-images.json) описывает телефон и планшет с условными адресом registry и digest. Замените их данными проверенного образа; пример не предназначен для запуска без изменений. Импортированные профили создаются выключенными. Для готового проверенного образа можно экспортировать профили после завершения сборки.

```json
{
  "version": 2,
  "profiles": [{
    "id": "android-qa",
    "name": "Android QA",
    "allowLaunchOverrides": null,
    "image": "registry.example.com/rdf-emulator@sha256:<64 hex characters>",
    "android": { "version": "16", "api": 36, "abi": "x86_64", "deviceType": "mobile" },
    "resources": { "cpu": 4, "memoryMb": 4096, "guestMemoryMb": 2048, "guestCores": 2, "diskGb": 8 },
    "emulator": { "params": ["-no-snapshot"] }
  }]
}
```

Этот фрагмент — шаблон: замените image действительным digest. `allowLaunchOverrides: null` наследует общее разрешение; `true`/`false` задают правило профиля.

Совместимость с уже подключёнными сторонними образами сохраняется: `container` допускает env, command/entrypoint и ограниченный список Docker-параметров; `launch` задаёт имена переменных аргументов/ADB и `farmFlags`. Новым образам, собранным каталогом, эти переопределения не нужны. Не импортируйте образы с отключённой ADB-авторизацией.

Значения `container.env` шифруются и не выдаются API/экспортом: `null` при обновлении сохраняет существующее значение. `SECRETS_KEY` храните отдельно от базы. Устройства, порты, тома, сеть/PID/IPC хоста и Docker socket запрещены в манифесте. Нераспознанные поля отклоняются. Формат GPU старых манифестов игнорируется с предупреждением.

## Проверка и очистка

Новые сборки до публикации проверяют загрузку Android, ADB-авторизацию и все сгенерированные форм-факторы. Для стороннего образа такую проверку выполняет администратор отдельно. Digest не подтверждает надёжность автора образа: ограничивайте источники через `AGENT_ALLOWED_IMAGE_PREFIXES`.

Каждая сессия получает отдельный контейнер и writable layer. После завершения контейнер и его анонимные тома удаляются; слот не освобождается при неподтверждённой очистке. Физические устройства возвращаются в выдачу только после полной проверенной очистки.
