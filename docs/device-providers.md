# Архитектура: провайдеры устройств

Агент больше не знает, «эмулятор это или телефон». Каждый тип устройства — отдельный **провайдер**
(`agent/src/providers/`), а `main.mjs` разговаривает только с `ProviderRegistry`.

```text
broker ──WS──► main.mjs ──► ProviderRegistry ──┬─► EmulatorProvider   (Docker + agent-control, слоты CPU/RAM, egress)
                 │  (WS, туннели, heartbeat)   └─► UsbAndroidProvider (физические Android по USB, общий adb-сервер)
                 └─► StreamManager / AppTransfers / AdbClient  (общие Android-блоки, внедряются в провайдеры)
```

## Общая модель устройства

Модель Android-устройства определена в shared/device-contract.schema.json. Типы и нормализаторы для агента, сервера, интерфейса и MCP, а также компоненты OpenAPI создаются одной командой:

    node scripts/sync-device-contract.mjs

Для генерации нужны установленные зависимости сервера. Проверка актуальности: node scripts/sync-device-contract.mjs --check. Созданные файлы не редактируются вручную.

Контракт содержит платформу, тип, идентификатор, состояние, версию ОС и возможности устройства. Неизвестные типы и платформы исключаются из списка. Неизвестное состояние считается непроверенным. Старые записи Android без поля платформы остаются совместимыми.

## Контракт (`base.mjs`)

| Метод | Назначение |
|---|---|
| `start / stop` | занять и освободить устройство (контейнер, телефон) |
| `recover / reconcile` | восстановить сессии после рестарта; найти сессии, чьё устройство пропало (отключили USB, упал контейнер) |
| `inventory` | что провайдер может предложить сейчас (уходит брокеру в `providers[]` heartbeat) |
| `tunnelTarget` | как строить ADB-туннель: `deviceTcp` и `adbServer: 'isolated' \| 'shared'`; `null` — туннеля нет |
| `ops` | таблица `action → handler`. Нет действия в таблице — «not supported for X devices» |
| `nodeOps` | действия уровня узла (политика слотов эмулятора) |

`capabilities` вычисляются из `ops`, и уточняются для конкретного устройства после чтения версии Android. Аудио требует Android 11 (API 30), видео и управление через scrcpy — API 21. При неудачном запросе версии эти функции не объявляются. Проверка не гарантирует наличие рабочего аппаратного кодека; ошибки запуска потока обрабатываются отдельно. Сведения USB-устройства обновляются при выдаче сессии и удаляются из памяти после отключения.

## Что общее, что разное

- `android-ops.mjs` — действия, которым нужен только adb-serial (shell, logcat, input, файлы, APK, scrcpy). Их используют
  и эмулятор, и USB-телефон — без копирования и без `if`.
- **Эмулятор**: Docker, KVM, учёт CPU/RAM, сеть egress, `env` (emu console). Туннель — отдельный adb-сервер на сессию.
- **USB Android**: аренда по serial (`adb devices -l`, только строки с `usb:`), без Docker. Туннель идёт через общий
  adb-сервер агента (он владеет USB), `AdbServerFilter` привязывает его к арендованному serial. После
  сессии телефон очищается (см. ниже). Нет `network`/`env`. Отключили кабель — `reconcile` освободит сессию.

## Сброс (wipe) и карантин — защита данных

Правило **fail closed**: устройство выдаётся в аренду только если оно заведомо чистое **и готово к работе**.

### Почему не «просто factory reset»

Голый factory reset на телефоне стирает данные, но заодно и **авторизацию adb / pairing**, а сам телефон оказывается на
мастере первоначальной настройки. Возвращать его в строй пришлось бы руками после каждой аренды. Поэтому контракт сброса —
**«стереть И вернуть в готовое состояние»**, а проверка смотрит и на чистоту, и на готовность.

| Тип | Сброс | Что проверяется |
|---|---|---|
| Эмулятор | уничтожается контейнер, том данных и сети (agent-control) | контейнера больше нет в списке агента |
| USB Android, `command` | явно заданный доверенный скрипт `AGENT_USB_WIPE_CMD <serial>` (без значения по умолчанию, см. [требования](usb-reset-script.md)): полный сброс + повторная подготовка (прошивка golden-образа через fastboot, zero-touch/Android Enterprise, Knox, recovery с зашитым adb-ключом агента) | adb снова авторизован, **сменился `boot_id`** (устройство реально перезагружалось), `user_setup_complete=1`, **канарейки**, посаженные при выдаче (строка в settings, файлы в `/data/local/tmp` и `/sdcard`), после сброса должны исчезнуть, затем проверки пользовательских приложений и хранилища. Код возврата скрипта сам по себе не доверяется |

Стратегии по умолчанию нет: `AGENT_USB_WIPE` обязателен. `partial` запрещён: повторная выдача требует полной очистки
и подходит лишь для лаборатории с одним доверенным пользователем. Если у телефонов нет способа автоматически вернуться в
готовое состояние после полного сброса (нет golden-образа/MDM), такие телефоны нельзя передавать между людьми. Подробности и
остаточные риски: [аудит безопасности](security-audit-devices.md).

Жизненный цикл физического устройства (`physical.mjs`, `quarantine-store.mjs`):

0. устройство выдаётся **только при положительной записи «чистое»** в хранилище. Новый телефон, потерянный или сброшенный файл
   состояния — это «не проверено», а не «чисто»: подключённый телефон из `AGENT_USB_ALLOWLIST` сначала автоматически очищается
   (раздел `maintain` в heartbeat), и только потом становится свободным;
1. перед выдачей на устройство ставятся **канарейки**, и оно помечается **dirty** на диске (`AGENT_STATE_DIR`, должен быть на постоянном томе).
   Если канарейки поставить нельзя, аренда отклоняется;
2. при `stop`/отключении кабеля выполняется wipe + verify **в фоне**: освобождение сессии не ждёт минуты сброса, а
   устройство всё это время в состоянии `cleaning` и никому не выдаётся;
3. успех — устройство снова свободно; **любая ошибка (в т.ч. wipe упал, устройство пропало)** — сессия всё равно завершается,
   устройство получает статус `quarantined`, не выдаётся, а админам уходит оповещение;
4. после `stop` запись о сессии на диске отвязывается: рестарт во время очистки **заново очистит** устройство, а не воскресит сессию.
   После рестарта агента, если телефон подключён и сессия ещё не завершена, она **восстанавливается** (обновление агента не
   обрывает работу; если брокер такой сессии не знает, он её убьёт и это запустит очистку). Не подключённое устройство очищается
   на старте, а при неудаче уходит в карантин;
5. на одно устройство одновременно идёт только одна очистка (блокировка). Вернуть устройство можно только успешной повторной очисткой: `POST /api/admin/hosts/:id/devices/sanitize {kind, deviceId}`.
   Если нет хранилища состояния или стратегии wipe — аренда отклоняется.

Эмулятор: если контейнер не удалось уничтожить, слот остаётся занятым (запись `cleanupPending`), удаление повторяется
каждый heartbeat; после 3 неудач админам уходит оповещение.

Оповещение: агент шлёт `device-alert`, сервер пишет аудит (`device.quarantined`), создаёт уведомление **всем админам**
(и вебхуки на событие `device.quarantined`) и отвечает `alert-ack`. Пока нет ack, агент повторяет алерт при каждом
переподключении. Состояние устройств (`free/busy/cleaning/quarantined`, причина) сохраняется в `hosts.devices`
и отдаётся в `hostJson.devices`.

## Модель на сервере

- Физическое устройство арендуется по паре (узел, устройство): `POST /api/sessions {hostId, deviceKind, deviceId}`.
  Выдаются только устройства в состоянии `free` из последнего heartbeat; уникальный индекс `sessions_active_device_idx`
  (миграция 025) гарантирует, что два пользователя не возьмут один телефон одновременно.
- Сессия хранит `device_kind`, `device_id` и **снимок возможностей** (`capabilities`). Неизвестный тип и отсутствующий список возможностей физического устройства не дают доступа к функциям. Для старых эмуляторов сохраняется совместимость с основными операциями; аудио требует подтверждённой версии Android.
- Доступ регулируется обычным списком профилей команды: служебные профили `device-usb-android` и 
  (отключены, в списках эмуляторов не видны).
- `GET /api/hosts` отдаёт `devices[]` (занятые активной сессией помечаются `busy` сразу, без ожидания heartbeat; причина карантина
  видна только админам).
- Интерфейс: кнопка «Физическое устройство» на обзоре; вкладки и кнопки сессии скрываются по `capabilities`
  (возможности устройства задаёт агент); админский раздел «Узлы» → «Физические устройства» с кнопкой «Повторить очистку».
- ADB-порт через брокер для USB-сессий не выдаётся (нужен прямой TCP к устройству); работа идёт через браузер и API.

## Включение

```sh
AGENT_USB_ENABLED=1            AGENT_USB_ALLOWLIST=R58M123ABC,ZX1G22   # allowlist необязателен
AGENT_USB_WIPE=command      AGENT_USB_WIPE_CMD=/abs/path/reset-android.sh   # обязательно; AGENT_USB_ALLOWLIST обязателен
AGENT_STATE_DIR=...            # по умолчанию ~/.android/rdf-state (том agent_adb_keys)
```

Docker-контейнер агента должен видеть устройства: `--device /dev/bus/usb` (или `privileged` отдельным USB-агентом),
Рекомендуется **отдельный агент на хосте с телефонами** (без `agent-control`/KVM),
а эмуляторы держать на других узлах: у них разные требования к привилегиям.

Старт сессии: `start` с `params.kind = 'emulator' | 'usb-android'` (по умолчанию `emulator`) и, для
физических, `params.deviceSerial` (иначе берётся первое свободное).

## Проверки и ограничения

Статус проверок и ограничения физической аренды находятся в [матрице проверок](verification.md#not-tested). Результаты тестов с моделью устройства не подтверждают очистку реального телефона.

## Безопасная повторная выдача

`AGENT_USB_WIPE=partial` больше не принимается, включая старый opt-in: он сохраняет приватные данные. Требуется `command` с полной очисткой и независимой проверкой. Состояние устройства записывается атомарно и синхронизируется на диск. Ошибка записи блокирует последующие выдачи; после устранения ошибки перезапустите агент и проверьте карантин.
