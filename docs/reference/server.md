# Сервер: API и обмен с агентом

[← Оглавление](../README.md) · [Примеры запросов](../api/README.md)

Этот справочник помогает найти нужную часть API и понять, где выполняется действие. Для установки используйте [руководство сервера](../deployment/server.md).

## Кто что выполняет

Сервер проверяет пользователя, права доступа и наличие свободного слота. Он сохраняет состояние в PostgreSQL и передаёт команду агенту. Агент запускает устройство и возвращает результат. У сервера нет доступа к Docker socket узла.

При старте сервер применяет миграции из `server/migrations` и создаёт первого администратора при необходимости. Первый профиль добавляется миграцией; остальные настраивает администратор. Каталог системных образов Google доступен администратору; выбранные образы собираются отдельными заданиями на узле-сборщике и публикуются в registry. Готовые профили создаёт фоновая проверка сервера. [Образы и registry](../deployment/registry.md).

## Авторизация

Запрос из браузера использует cookie сессии. Скрипт передаёт токен:

```http
Authorization: Bearer <API-токен>
```

Личный токен действует с правами своего пользователя. Системный — с правами администратора. Токен показывается при создании, в базе хранится его хеш.

При запросе чужого или уже удалённого объекта API может вернуть `404`. Поэтому одного кода `404` недостаточно, чтобы сделать вывод, что объект никогда не существовал.

## Жизненный цикл сессии

```text
POST /api/sessions → 202, starting
                         ↓
                       running
                         ↓
DELETE /api/sessions/:id → stopping → очистка → 404
```

`202` подтверждает принятие операции, а не готовность устройства. Клиент ждёт `running`, опрашивая сессию. При неудачном запуске агент также должен очистить ресурсы. Пока очистка не подтверждена, слот может оставаться занятым.

После освобождения активная запись и ADB-доступ удаляются. Краткая история аренды и аудит хранятся отдельно; это не снимок данных Android.

## Соединение агента

Агент открывает WebSocket на `/agent/connect` и передаёт свой токен в заголовке `Authorization`. Токен привязан к ID узла.

Агент отправляет описание узла и периодические сообщения о его состоянии. Сервер отправляет команды с ID запроса и сессии; агент отвечает результатом с тем же ID. В числе команд — запуск, остановка, управление экраном, передача файла и запрос сведений об Android.

Реализация: [серверная сторона](../../server/src/agent.ts), [цикл агента](../../agent/src/main.mjs). Изменения протокола проверяйте с обеими сторонами: обновление одного веб-интерфейса не обновляет агента.

## Экран и звук

Браузер подключается к `/api/sessions/:id/stream`. Сервер проверяет доступ к сессии и передаёт медиасообщения агента. События касаний и клавиш идут по этому же соединению.

Видео приходит как H.264 либо отдельные PNG-кадры. Звук передаётся отдельным потоком при наличии поддержки. Клиентская реализация находится в [useSessionStream.ts](../../frontend/src/useSessionStream.ts).

## ADB

Есть два разных способа работы:

- **HTTP-команды и браузерная консоль:** запрос идёт через API и агент к выбранному устройству. Публиковать ADB-порты не нужно.
- **Обычный `adb connect`:** сервер выдаёт порт своего ADB-посредника и проверяет публичный ключ пользователя. Нужен отдельно опубликованный диапазон TCP-портов.

Ключ агента и ключ пользователя выполняют разные задачи. Не заменяйте ключ агента пользовательским. [Настройка ADB для пользователей](../guides/sessions.md).

## Метрики

`GET /metrics` включается при заданном `METRICS_TOKEN` длиной не менее 16 символов. Запрос должен содержать `Authorization: Bearer <METRICS_TOKEN>`. Без настройки маршрут возвращает `404`.

В стандартной конфигурации nginx этот путь наружу не проксируется. Для Prometheus настройте доступ к API внутри сети развёртывания или отдельное правило своего reverse proxy с сохранением проверки токена. Путь `/health` тоже доступен непосредственно на API; готовая команда проверки есть в [диагностике](../troubleshooting.md).

## Выбор устройства и параметры запуска

Сохранённые пресеты удалены. В новой сессии пользователь выбирает включённый профиль устройства из одного списка. История аренды сохраняется.

Общее разрешение изменения ресурсов, хранилища и аргументов эмулятора задаётся администратором в разделе «Профили устройств → Параметры запуска пользователей». API: `GET/PATCH /api/admin/launch-settings`, тело изменения `{ "allowLaunchOverrides": true }`. По умолчанию изменение запрещено.

Поле профиля `allowLaunchOverrides` переопределяет это разрешение: `null` — наследовать, `true` — разрешить, `false` — запретить. Оно входит в экспорт и импорт манифестов. `/api/profiles` возвращает также вычисленное `launchOverridesAllowed`.

Проверка выполняется на сервере перед резервированием слота и при постановке в очередь; разрешение повторно проверяется при назначении узла. При отзыве разрешения заявка с изменёнными параметрами отменяется с `launch_overrides_forbidden`. Значения по умолчанию не требуют разрешения. Изменять профиль или обходить ограничения узла через параметры сессии нельзя: пользователи не могут увеличивать CPU/RAM сверх профиля, хранилище ограничено максимумами, privileged доступен только администраторам с разрешением узла.

Выбор GPU, личного ADB-ключа и количества устройств не зависит от разрешения на параметры. GPU определяется возможностями узла. Администраторы всегда могут изменять параметры запуска в пределах поддерживаемых значений и лимитов узла.
