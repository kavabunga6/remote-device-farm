## Править UI и сразу видеть результат

Для обычной работы над интерфейсом достаточно Node.js 24, npm и доступа к запущенной ферме. Локальная база и агент не нужны.

```sh
cd frontend
npm ci
npm run dev:live -- https://farm.example.com
```

Откройте **http://localhost:5173**. При локальном входе или LDAP используйте логин и пароль от указанной фермы. При сохранении файлов Vite обновляет страницу автоматически; пересобирать Docker-контейнер не требуется.

Это интерфейс с **реальными данными**: создание и завершение сессий, смена настроек и загрузка APK происходят на подключённом сервере.

Если у тестового сервера самоподписанный сертификат:

```sh
npm run dev:live -- https://farm.example.com:8443 --insecure
```

`--insecure` отключает проверку сертификата только в локальном прокси. Для обычного подключения используйте доверенный сертификат.

Вход через OIDC/SSO требует отдельной настройки: текущий callback возвращает браузер на `PUBLIC_URL`, а cookie локального UI находится на `localhost`. Для отладки OIDC используйте отдельный backend с локальным `PUBLIC_URL` и соответствующим callback в настройках провайдера.

### Другой порт

Bash:

```sh
DEV_PORT=5175 npm run dev:live -- https://farm.example.com
```

PowerShell:

```powershell
$env:DEV_PORT = '5175'
npm run dev:live -- https://farm.example.com
```

Если порт занят, остановите предыдущий процесс через `Ctrl+C` или выберите другой. Для перезапуска запустите ту же команду снова.

## Работать только над вёрсткой

```sh
cd frontend
npm ci
npm run dev:mock
```

Этот режим использует демонстрационные данные. Устройства и команды в нём не настоящие, а результат не проверяет работу сервера. Не используйте названия образов из mock-данных как каталог для развёртывания.

## Сохранение длинных форм

Формы с ручным сохранением используют `FormSaveActions` из `frontend/src/FormSaveActions.tsx`. Компоненту передаются ID формы, признак изменений и состояние запроса. Если обычная кнопка ушла за пределы экрана, панель сохранения появляется внизу рабочей области. Она скрывается после сохранения, возврата к исходным значениям или скрытия формы. Обе кнопки отправляют ту же форму с её проверками полей.

Настройки с автоматическим сохранением и диалоги с закреплёнными кнопками используют свои элементы управления.

## Запустить backend из исходников

Самый короткий путь к локальному backend — [Docker Compose для сервера](deployment/server.md). Веб можно оставить в Vite и подключить его к `http://localhost:8088`:

```sh
cd frontend
npm run dev:live -- http://localhost:8088
```

Если нужно отлаживать сам Node.js-сервер, подготовьте PostgreSQL и задайте переменные из [`.env.example`](../.env.example), включая `DATABASE_URL`. Файл `.env` автоматически читает Compose; обычный `npm run dev` его не загружает. Например, из корня репозитория, с уже заполненным `.env` и запущенным PostgreSQL:

```sh
cd server
npm ci
```

Затем задайте `DATABASE_URL` на доступную из вашей ОС базу и остальные переменные через окружение терминала или настройки IDE. В каталоге `server` выполните:

```sh
npm run dev
```

Сервер слушает порт `8080`, если `PORT` не задан. Миграции выполняются при старте. PostgreSQL из базового Compose наружу не опубликован: для запуска Node.js на хосте нужен отдельный экземпляр БД либо явное локальное перенаправление порта.

## Проверки перед отправкой изменений

Выполняйте проверки той части, которую меняли. Команды ниже запускаются из корня репозитория:

```sh
# Интерфейс: TypeScript, сборка и модульные тесты
npm --prefix frontend run build
npm --prefix frontend test

# Публичные тексты, ссылки и скриншоты
node scripts/check-public-content.mjs
node scripts/check-repository-privacy.mjs

# Сервер
npm --prefix server run build
npm --prefix server test

# Агент
npm --prefix agent test
```

Предварительно установите зависимости соответствующей части через `npm --prefix <каталог> ci`. Docker/KVM-зависимые сценарии агента требуют Linux-узла; локальная проверка на Windows не заменяет запуск устройства.

## Где искать код

| Каталог | Что внутри |
| --- | --- |
| `frontend/src` | Страницы, компоненты, API-клиент и работа с видеопотоком |
| `frontend/dev` | Прокси к реальной ферме и демонстрационный API |
| `server/src/routes` | HTTP API |
| `server/migrations` | Изменения схемы PostgreSQL |
| `agent/src` | Управление устройствами, Docker и соединением с сервером |
| `docs` | Пользовательские и эксплуатационные инструкции |

Пароли, токены, сертификаты и локальные адреса не добавляйте в примеры для репозитория. Для конфигурации используйте `.env` и `.env.agent`, которые исключены из Git.

## Проверки API и интерфейса

Из корня репозитория:

```sh
npm --prefix server ci
npm --prefix frontend ci
npm --prefix server run test:contracts
npm --prefix frontend exec -- playwright install chromium
npm --prefix frontend run e2e:api
```

`test:contracts` сравнивает HTTP-маршруты и основные права доступа с OpenAPI, проверяет пути и методы API-клиента, затем проверяет реальные HTTP-ответы по OpenAPI и типам данных UI. Проверяются cookie и личные токены, отказ при отсутствии прав, изоляция владельцев, очередь, запуск и фоновое освобождение сессии.

`e2e:api` запускает Vite и сервер с рабочими маршрутами, авторизацией и миграциями. База PGlite и каталог APK создаются временно и удаляются после остановки. Агент заменён моделью ответов RPC: Docker, Android и внешние службы не запускаются. Браузерные сценарии проверяют вход и выход, создание сессии, прокси Android, назначение роли и отказ в доступе через UI и Bearer-токен. Наблюдаемые JSON-запросы и ответы сверяются с OpenAPI и типами клиента.

Сервер и Vite слушают только `127.0.0.1`. Порт UI по умолчанию — `5192`; для другого порта задайте `API_UI_PORT`. Существующий сервер на этом порту не используется. Набор `npm --prefix frontend run e2e` продолжает работать с демонстрационным API.

Проверки PNG и WebM в браузерном наборе требуют Chrome и FFmpeg: команды `ffmpeg` и `ffprobe` должны быть доступны в `PATH`. Пиксели проверяются в скачанных файлах, а не в предпросмотре браузера. `CAPTURE_CPU_THROTTLE=4` включает четырёхкратное замедление CPU на время записи.

Эти тесты не подтверждают запуск реального устройства, обработку RPC настоящим агентом, PostgreSQL под нагрузкой или внешнюю OIDC/LDAP-авторизацию. Проверки окружения перечислены в [ограничениях](verification.md).

## CI test runtime

Server and frontend API fixtures use Node.js 22 LTS in CI. Their PGlite test
database exercises WebAssembly teardown, which can trigger the upstream
[Node.js 24 code-GC issue](https://github.com/nodejs/node/issues/66366).
Agent, integration packages and media checks use Node.js 24. Production
containers are still built and checked with their configured runtime;
PGlite is a development dependency.
