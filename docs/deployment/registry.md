# Registry и сборка образов

[Установка сервера](server.md) · [Образы и профили](../guides/images.md) · [OpenAPI](../api/openapi.yaml)

## Управление и очистка через интерфейс

**Администрирование → Образы**: версии registry, удаление с отключением связанных профилей, локальный кэш узлов, политики хранения и история заданий. См. [пошаговое руководство](../guides/image-management.md). Сервис registry собирается из `deploy/registry`; том `registry_data` прежний, дополнительный `registry_control` содержит закрытый токен обслуживания и состояние supervisor. Сервер читает токен из тома, не получая Docker-сокет.

## Один домашний Linux-хост

Для **новой** установки есть подготовка конфигурации без настройки Docker daemon, firewall или сети хоста. Нужны Node.js 24, OpenSSL, Docker Engine 28+, Compose v2 и `/dev/kvm`:

```bash
node scripts/init-local.mjs
docker compose -f compose.yaml -f compose.agent.yaml -f compose.override.yaml up -d --build
```

Скрипт создаёт `.env`, `.env.agent`, сертификат nginx и `compose.override.yaml`. Существующие файлы он не перезаписывает. Пароли, токен агента и `SECRETS_KEY` генерируются локально и не печатаются. Сохраните `SECRETS_KEY` в менеджере секретов; пароль администратора лежит в `.env` под именем `LOCAL_ADMIN_PASSWORD`.

Панель открывается по `http://localhost:8088`. Это локальный secure context браузера. Registry доступен Docker daemon на **этом же хосте** по `localhost:5000`. Порт привязан к `127.0.0.1`; каждый запрос проходит через nginx и проверку временных credentials фермы. Сам `registry:5000` наружу не публикуется. Docker разрешает HTTP для loopback registry по умолчанию; файл `daemon.json` скрипт не меняет. [Правило loopback в документации Docker](https://docs.docker.com/reference/cli/dockerd/#insecure-registries).

Если Linux-хост без рабочего стола, панель можно открыть через SSH-туннель с компьютера пользователя: `ssh -N -L 8088:127.0.0.1:8088 user@node`, затем `http://localhost:8088`. Для общего доступа без туннеля настройте HTTPS по следующему разделу.

`RDF_BUILTIN_REGISTRY_ADDRESS=localhost:5000` заполняет только отсутствующий адрес в БД. `RDF_AUTO_IMAGE_BUILDER=true` разрешает автоматически выбрать единственный подключённый, включённый KVM-узел поддерживаемой архитектуры. При нескольких узлах сборщик выбирается явно в каталоге. Ранее выбранный сборщик не заменяется.

### Стартовый набор

Стартовый legacy-профиль остаётся выключенным до полной runtime-проверки. Для новой установки создайте образ через каталог SDK. Доступность пакетов, загрузка Android и аутентификация проверяются отдельно: наличие профиля не означает, что образ уже скачан или одобрен для запуска.

Для нового Android откройте **Профили устройств → Каталог образов**, выберите пакет и нажмите **Собрать**. Для начала достаточно одного пакета `google_apis` нужного API: современные мобильные образы дают профили телефона и планшета. ТВ, Automotive и Wear требуют соответствующих SDK-пакетов. Не запускайте весь каталог сразу: один образ занимает несколько гигабайт, сборка скачивает SDK и расходует ресурсы хоста. Android старых версий/форм-факторов доступен только если Google публикует совместимый SDK-пакет; отсутствующие варианты каталог не выдумывает.

Сборка, проверка и отправка в registry выполняются в фоне. До публикации каждого нового образа сборщик загружает Android в отдельном временном контейнере: проверяет `sys.boot_completed=1`, `ro.adb.secure=1`, отказ ADB-клиенту с чужим ключом, ресурсы и экран каждого сгенерированного профиля. Дополнительно проверяет аппаратный рендерер, если сборщик имеет готовые NVIDIA/DRI. В каталоге этот этап называется **«Проверка загрузки Android и ADB»**, его можно остановить. Ошибка проверки запрещает push и создание новых профилей; предыдущая сборка остаётся доступна. Уже собранные образы повторно не проверяются.

Проверка требует KVM, свободного сборщика и как минимум 2 ГБ свободной памяти сверх лимита проверяемого контейнера. Она использует отдельную внутреннюю Docker-сеть без опубликованных портов и удаляет свои контейнеры/сети после успеха, ошибки или отмены. Пользовательский запуск имеет приоритет: проверка уступает узел и повторяется после освобождения. Для одного варианта и одного режима ожидание загрузки ограничено 10 минутами. Профили создаёт сервер после подтверждённого push и digest, даже если каталог закрыт. Перезапуск `agent-control` не скрывает незавершённые задачи: они отмечаются ошибкой прерывания, и их можно повторить. Для этого `agent_image_builds` должен сохраняться между пересозданиями агента.

## Несколько узлов и HTTPS

`localhost:5000` нельзя использовать для второго узла: на нём это другой Docker daemon и другой loopback. Укажите единый адрес, например `farm.example.com:8443`, доступный **каждому** узлу. Адрес в настройке не содержит `https://` и `/v2/`; nginx публикует протокол registry под `/v2/` автоматически.

1. Поднимите `registry` вместе с `server` и `web` из `compose.yaml`.
2. Настройте доверенный HTTPS-сертификат на `web` или внешнем reverse proxy. При внешнем proxy передавайте `/v2/` целиком, `Authorization`, исходный `Host`, протокол, разрешите большие тела и длительные загрузки без буферизации. Не добавляйте вторую Basic-аутентификацию перед `/v2/`.
3. В **Каталоге образов → Registry** выберите встроенный registry и его адрес. Для новой установки можно задать `RDF_BUILTIN_REGISTRY_ADDRESS`; сохранённую настройку переменная не перезаписывает.
4. Добавьте префикс `<адрес>/rdf-emulator` в `AGENT_ALLOWED_IMAGE_PREFIXES` узлов, если ограничение включено. Не удаляйте другие используемые разрешённые префиксы.
5. Выберите сборщик, соберите один пакет и проверьте запуск на другом узле по тому же `@sha256:…`.

Проверка nginx и доступности без пароля:

```bash
docker compose exec -T web nginx -t
curl --cacert certs/ip.crt --include https://farm.example.com:8443/v2/
```

Без credentials ожидается **401** с `WWW-Authenticate`, а не 200. При штатном запуске сервер выдаёт агенту временный токен: pull на скачивание, push на публикацию. API-токен пользователя не является паролем registry. Registry хранит только образы, а настройки и хеши временных токенов — PostgreSQL.

### Частная CA

Доверие браузера и доверие Docker daemon на узле — разные настройки. Если сертификат выдан вашей CA, установите **сертификат CA**, не приватный ключ, в `/etc/docker/certs.d/farm.example.com:8443/ca.crt` на каждом Docker-хосте. Путь должен в точности совпадать с адресом registry, включая порт. Проверьте корпоративные правила перезапуска Docker до применения изменений: на общем сервере он затронет другие контейнеры. Ферма сама не меняет конфигурацию daemon. [Настройка CA для registry](https://docs.docker.com/engine/security/certificates/).

### HTTP registry в изолированной лаборатории

Для loopback `localhost:5000` дополнительная настройка обычно не нужна. Для HTTP registry на сетевом адресе Docker требует `insecure-registries`. Это глобальная настройка daemon, которая разрешает передачу credentials без TLS. Она не подходит для обычного доступа через недоверенную сеть.

Если администратор сознательно выбрал этот режим, **добавьте** адрес к существующему массиву, сохранив остальные настройки `/etc/docker/daemon.json`, например:

```json
{ "insecure-registries": ["192.0.2.10:5000"] }
```

Проверьте `dockerd --validate --config-file=/etc/docker/daemon.json`; применяйте перезапуск Docker только в согласованное окно обслуживания. Ни quickstart, ни агент не выполняют эту операцию автоматически. Для штатной установки предпочтительнее HTTPS с доверенной CA.

## Внешний registry

В каталоге выберите **Внешний**, укажите `host[:port][/prefix]`, имя пользователя и пароль с правами push/pull только в нужный repository. Пароль зашифрован через `SECRETS_KEY` и не возвращается API. При смене registry старые образы и ссылки профилей не копируются: сначала соберите/перенесите образ в новом registry, затем обновите профили.

## Ресурсы, бэкапы и обслуживание

Сверяйте лимит памяти/CPU профиля с настройками слота. Лимит контейнера включает Android и накладные расходы эмулятора. Нельзя уменьшать его до памяти Android без запаса. Сборка и холодная загрузка образа также требуют свободного диска и сети.

Сохраняйте `registry_data` **вместе с** базой и `app_store`: в БД закреплены digest, а содержимое этих digest находится в registry. Команда резервного копирования и порядок восстановления приведены в [установке сервера](server.md#резервные-копии-и-перенос). Том `agent_image_builds` сохраняет журнал сборок на узле; `/home/agent/.android` содержит отдельные ключи/состояние агента.

Перед выпуском выполните [проверки реальных образов](../release-checklist.md#3-образы-и-профили). Тесты с подделкой Docker не подтверждают загрузку Android, безопасность ADB или аппаратный рендеринг.

### Прогреть образы до первого запуска

Администратор может поставить фоновые скачивания через `POST /api/admin/emulator-images/prewarm` с `{}` для всех включённых профилей по digest и включённых узлов, либо ограничить запрос `hostIds` и `profileIds`. `POST` возвращает числа `queued` и `skipped`. `GET` того же endpoint возвращает `items` со статусами `queued`, `pulling`, `done`, `failed` и ошибками. Используется пользовательский API-токен администратора. Повторный запрос не создаёт вторую загрузку того же образа на том же узле. Прогрев не занимает слот и не запускает Android; отдельная реальная проверка загрузки всё равно нужна.

### Удалить неиспользуемые digest

Сначала получите план: `docker compose exec -T server node dist/registry-cleanup.js`. По умолчанию CLI ничего не удаляет. Он защищает digest, используемые неудалёнными профилями, неизменяемыми `launch_image` активных сессий, текущими сборками каталога и заданиями прогрева. Обычный тег, digest которого ещё не зарегистрирован в каталоге или квитанциях завершённых сборок, попадает в `unreconciledTags`: такой образ сохраняется, а `--apply` отказывает до синхронизации. Это защищает образ, опубликованный перед отключением сервера. Ошибка чтения registry останавливает очистку.

Перед обслуживанием подключите все узлы, включая бывших сборщиков. Дождитесь окончания сборок и фонового импорта: активных задач быть не должно, все завершённые и прерванные задачи должны получить серверную квитанцию и подтверждение ACK. Если план содержит `unreconciledTags`, сначала разберите эти публикации и выполните синхронизацию; не обходите отказ удалением записей из базы.

Для применения запланируйте окно обслуживания. Остановите API и сборщиков, дождитесь не менее 90 секунд после последнего heartbeat узлов и убедитесь, что нет активных сессий. В отдельном одноразовом контейнере выполните:

```bash
docker compose run --rm --no-deps server node dist/registry-cleanup.js --apply --maintenance
```

`--maintenance` подтверждает остановку записи оператором; сам CLI не останавливает сервисы и не меняет Docker daemon. Он работает только со встроенным registry. Внутренний адрес по умолчанию `http://registry:5000`, переопределение — `RDF_REGISTRY_MAINTENANCE_URL`. Не публикуйте этот обходящий nginx внутренний порт наружу.

Удаление манифеста ещё не освобождает blobs. [Условия безопасной сборки мусора Distribution](https://distribution.github.io/distribution/about/garbage-collection/). После удаления остановите `registry`, чтобы во время mark-and-sweep не шли push, и запустите сборку мусора на его томе.

**Условие для `--delete-untagged`:** до остановки все текущие и бывшие сборщики были подключены, активных сборок не осталось, все терминальные задачи успешно импортированы и подтверждены ACK. CLI не проверяет журналы отключённых агентов и не может обнаружить старую ещё не импортированную публикацию, тег которой уже перезаписала следующая сборка. Если это условие не доказано, уберите `--delete-untagged` из обеих команд ниже: обычный GC освободит blobs удалённых манифестов, сохранив неизвестные публикации без тегов.

```bash
docker compose stop registry
docker compose run --rm --no-deps --entrypoint registry registry garbage-collect --dry-run --delete-untagged /etc/docker/registry/config.yml
# Проверьте план удаления, затем:
docker compose run --rm --no-deps --entrypoint registry registry garbage-collect --delete-untagged /etc/docker/registry/config.yml
docker compose up -d registry server web
```

Перед очисткой сохраните проверенный бэкап. После неё проверьте pull используемых digest, возобновите агенты/сборщиков и убедитесь, что каталог и прогрев работают. Политику удаления внешнего registry настраивайте средствами его оператора.
