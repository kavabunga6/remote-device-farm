# Развёртывание сервера

[Документация](../README.md) · [Подключение агента](agent.md)

Сервер хранит пользователей, настройки и сессии. Агент запускает устройства на узле и передаёт их экран в браузер. Сервер и агент можно разместить на одном Linux-хосте или на разных машинах.

Основной `compose.yaml` поднимает четыре сервиса:

| Сервис | Что делает |
| --- | --- |
| `web` | Отдаёт интерфейс и направляет API и WebSocket-запросы серверу |
| `server` | Проверяет доступ, назначает слоты, общается с агентами |
| `postgres` | Хранит учётные записи и настройки |
| `registry` | Хранит собранные образы Android, доступные через `/v2/` у `web` |

KVM и образы Android нужны **узлу с агентом**. Сам сервер не запускает устройства.

## Быстрый запуск

Для новой установки на одном Linux-хосте можно выполнить `node scripts/init-local.mjs`: он подготовит пароли, ключ шифрования, локальный registry и агента. [Подробный локальный старт и переход на несколько узлов](registry.md). Ниже — ручная установка с HTTPS.

Понадобятся Linux, Git, OpenSSL, Docker Engine и Docker Compose 2.30+ с BuildKit с поддержкой `additional_contexts`. Команды выполняются от пользователя, которому доступен Docker. Проверить установку:

```bash
docker version
docker compose version
```

### Если загрузка зависимостей недоступна

Сборка скачивает npm-пакеты, а сборщик образов — Android SDK. Проверьте доступ
к `registry.npmjs.org` и `dl.google.com` с хоста и из Docker. Если в вашей сети
требуется HTTP-прокси, передайте его только на время сборки; адрес должен быть
доступен из build-контейнера (его `127.0.0.1` — сам контейнер).

```bash
docker compose -f compose.yaml -f compose.agent.yaml -f compose.override.yaml build \
  --build-arg HTTP_PROXY=http://proxy.example.com:3128 \
  --build-arg HTTPS_PROXY=http://proxy.example.com:3128
docker compose -f compose.yaml -f compose.agent.yaml -f compose.override.yaml up -d --no-build
```

Это не меняет Docker daemon или сетевые правила. Не записывайте пароль прокси
в Dockerfile, Git или публичные журналы. Доступ сборщика к Android SDK —
отдельная настройка сети узла; успешная npm-сборка его не подтверждает.

### 1. Скачать проект

```bash
git clone https://github.com/kavabunga6/remote-device-farm.git
cd remote-device-farm
```

### 2. Создать настройки

Следующий пример — для **новой установки**. Замените `192.0.2.10` на IP вашего сервера; для запуска на своём компьютере используйте `127.0.0.1`. Если `.env` уже существует, отредактируйте его: не перезаписывайте текущие пароли и токен агента.

```bash
umask 077
FARM_HOST=192.0.2.10
cat > .env <<EOF
POSTGRES_DB=devicefarm
POSTGRES_USER=devicefarm
POSTGRES_PASSWORD=$(openssl rand -hex 24)
HTTP_PORT=8088
PUBLIC_URL=https://${FARM_HOST}:8443
COOKIE_SECURE=true
TRUST_PROXY=1
SECRETS_KEY=$(openssl rand -base64 32)
RDF_BUILTIN_REGISTRY_ADDRESS=${FARM_HOST}:8443
RDF_AUTO_IMAGE_BUILDER=true

AUTH_MODE=local
LOCAL_ADMIN_USERNAME=admin
LOCAL_ADMIN_PASSWORD=$(openssl rand -hex 16)

BOOTSTRAP_AGENT_ID=agent-1
AGENT_TOKEN=$(openssl rand -hex 32)
EOF
```

Пароль БД в примере состоит из шестнадцатеричных символов: его можно безопасно подставлять в строку подключения без дополнительного URL-кодирования. `.env` содержит секреты; не добавляйте его в Git.

### 3. Подключить сертификат и HTTPS-порт

Встроенный `web` ожидает сертификат и ключ. Этот шаг обязателен: без файлов nginx не запустится, даже если открывать HTTP-порт.

Для первого знакомства создайте тестовый сертификат на 30 дней. Выполняйте команды в том же терминале, где задан `FARM_HOST`:

```bash
mkdir -p certs
openssl req -x509 -newkey rsa:2048 -nodes -sha256 -days 30 \
  -subj "/CN=${FARM_HOST}" \
  -addext "subjectAltName=IP:${FARM_HOST}" \
  -keyout certs/ip.key -out certs/ip.crt

cat > compose.override.yaml <<'YAML'
services:
  web:
    ports:
      - "8443:443"
    volumes:
      - ./certs/ip.crt:/etc/nginx/tls/ip.crt:ro
      - ./certs/ip.key:/etc/nginx/tls/ip.key:ro
YAML
```

Compose автоматически добавит `compose.override.yaml` к основному файлу. Сохраните оба файла в каталоге установки. Каталог `certs/` уже исключён из Git.

Браузер предупредит о самоподписанном сертификате. Для временной проверки можно подтвердить исключение для своего сервера. Для обычной работы установите сертификат, которому доверяют компьютеры пользователей и агентов: например, от вашей корпоративной CA. Поместите сертификат с цепочкой в `certs/ip.crt`, ключ — в `certs/ip.key`.

### 4. Запустить контейнеры

```bash
docker compose up -d --build
docker compose ps
```

При первом старте сервер сам создаёт таблицы БД и учётную запись администратора. Проверить, что он отвечает и видит PostgreSQL:

```bash
docker compose exec -T server node -e "fetch('http://127.0.0.1:8080/health').then(async r => { console.log(await r.text()); if (!r.ok) process.exit(1) }).catch(e => { console.error(e.message); process.exit(1) })"
```

Ожидаемый ответ — `{"ok":true}`. Проверить путь от браузера до API:

```bash
curl --fail --cacert certs/ip.crt "https://${FARM_HOST}:8443/api/config"
```

### 5. Войти и подключить узел

Откройте `https://<IP-сервера>:8443`, например [https://192.0.2.10:8443](https://192.0.2.10:8443). Логин — `admin`. Получить созданный пароль:

```bash
sed -n 's/^LOCAL_ADMIN_PASSWORD=//p' .env
```

После входа подключите [первого агента](agent.md). На том же хосте агент может подключаться к HTTP-порту через `ws://host.docker.internal:8088/agent/connect`; для удалённого агента используйте `wss://` с доверенным сертификатом. Пока агентов нет, список узлов пуст и запустить устройство негде.

Пароль можно сменить в профиле пользователя. Изменение `LOCAL_ADMIN_PASSWORD` в `.env` **не меняет пароль уже созданной учётной записи**.

## Доступ с другого компьютера

Для работы с экраном устройства используйте HTTPS с доверенным сертификатом. HTTP на `localhost` подходит для локальной разработки; HTTP по IP узла не даёт браузеру всех возможностей, необходимых для видеопотока.

После замены сертификата выполните `docker compose restart web`, чтобы nginx перечитал файлы.

`PUBLIC_URL` должен совпадать с адресом, который пользователи открывают в браузере, включая схему и нестандартный порт. Например:

```dotenv
PUBLIC_URL=https://farm.example.com
COOKIE_SECURE=true
```

Изменения `.env` применяются при пересоздании контейнера:

```bash
docker compose up -d server
```

### Если HTTPS уже обслуживает reverse proxy

Направьте прокси на опубликованный HTTP-порт `web` — `8088`. Он должен передавать весь сайт, включая `/api/`, `/agent/` и `/v2/`, и поддерживать WebSocket: `Upgrade`, `Connection`, HTTP/1.1 и длительное соединение без буферизации.

Для схемы «внешний прокси → `web` → `server`» укажите:

```dotenv
PUBLIC_URL=https://farm.example.com
COOKIE_SECURE=true
TRUST_PROXY=2
```

Если прокси работает на этой же машине, HTTP-порт можно привязать только к loopback:

```dotenv
HTTP_PORT=127.0.0.1:8088
```

В `compose.override.yaml` уберите публикацию `8443:443` из раздела `web.ports`, сохранив `volumes` с сертификатами. Тогда прямой внешний доступ к `web` закроется, и клиенты будут приходить через ваш HTTPS-прокси.

После изменения привязки порта пересоздайте `web`:

```bash
docker compose up -d web server
```

В этом варианте агент подключается к `wss://farm.example.com/agent/connect`. Не используйте адрес `localhost` для агента на другой машине: для него это его собственный хост.

### Отдельный адрес для фронтенда разработки

Если API работает на сервере, а Vite открыт локально, разрешите второй адрес:

```dotenv
PUBLIC_URL=https://farm.example.com
FRONTEND_ORIGIN=http://localhost:5173
```

Это разрешение проверяется при запросах из браузера. Настройка локального proxy описана в [руководстве по разработке](../development.md).

## Подключение обычным `adb connect`

Браузерная консоль работает без опубликованных ADB-портов. Этот раздел нужен, если разработчики будут подключать Android Studio или локальный `adb`.

Добавьте в `.env` адрес сервера, доступный компьютерам разработчиков, и диапазон портов:

```dotenv
ADB_PUBLIC_HOST=192.0.2.10
ADB_PORT_START=15555
ADB_PORT_COUNT=8
```

Здесь и ниже `192.0.2.10` — пример. Замените его адресом вашего сервера в рабочей сети или VPN.

Дополните уже созданный `compose.override.yaml`: добавьте раздел `server` рядом с `web`. Сохраните настройки сертификатов и HTTPS-порта из быстрого запуска:

```yaml
services:
  server:
    ports:
      - "192.0.2.10:15555-15562:15555-15562"
```

Compose автоматически читает этот файл вместе с основным. Применить:

```bash
docker compose up -d server
```

Диапазон публикуется на **сервере**, а не на агенте. Диапазон даёт восемь портов для ADB-доступа к сессиям; это не настройка числа слотов.

Пользователь добавляет публичный ADB-ключ в своём профиле, выбирает его при запуске устройства и копирует готовую команду из заголовка сессии. Например:

```bash
adb connect 192.0.2.10:15555
```

Сервер проверяет ключ перед подключением. Последующий ADB-трафик по TCP не шифруется, поэтому эти порты предназначены для доверенной сети или VPN. Порт `5555` контейнера Android публиковать не нужно.

## Основные настройки

Полный шаблон находится в [`.env.example`](../../.env.example).

| Переменная | Значение и назначение |
| --- | --- |
| `PUBLIC_URL` | Адрес панели в браузере. Пример: `https://farm.example.com` |
| `HTTP_PORT` | Публикация HTTP-порта `web`, по умолчанию `8088` |
| `COOKIE_SECURE` | `true` для HTTPS, `false` для локального HTTP |
| `TRUST_PROXY` | Число прокси перед API: `1` для встроенного `web`, `2` при дополнительном внешнем прокси |
| `BOOTSTRAP_AGENT_ID` | ID первого агента, должен совпасть с его `AGENT_ID` |
| `AGENT_TOKEN` | Общий секрет сервера и первого агента, минимум 32 символа. Для дополнительных агентов создавайте отдельные токены |
| `SECRETS_KEY` | Ключ шифрования значений переменных контейнера в профилях. Создайте один раз (`openssl rand -base64 32`) и храните отдельно от бэкапов базы. Без него ключ создаётся автоматически и лежит в базе. **Потеряете ключ — значения придётся ввести заново** |
| `MAX_SESSIONS_PER_USER` | Одновременные сессии пользователя: по умолчанию `3`, `0` отключает лимит. Администраторов лимит не ограничивает |
| `IDLE_TIMEOUT_MINUTES` | Освобождение после простоя: по умолчанию `0` — выключено; например, `60` — один час |
| `MAX_SESSION_HOURS` | Предельная длительность сессии; по умолчанию `0` — выключено |
| `QUEUE_TTL_MINUTES` | Время ожидания в очереди, по умолчанию `30` минут |
| `APP_STORE_MAX_FILE_MB` | Максимальный APK в библиотеке пользователя, по умолчанию `200` МиБ |
| `APP_STORE_MAX_MB_PER_USER` | Объём библиотеки пользователя, по умолчанию `1024` МиБ |

### Способы входа

Включается один режим `AUTH_MODE`:

| Режим | Что заполнить |
| --- | --- |
| `local` | `LOCAL_ADMIN_USERNAME`, `LOCAL_ADMIN_PASSWORD` от 12 символов. Остальных пользователей создаёт администратор |
| `ldap` | `LDAP_URL` с `ldaps://`, `LDAP_BASE_DN`, `LDAP_BIND_DN`, `LDAP_BIND_PASSWORD`. В `LDAP_USER_FILTER` должно быть `{{username}}` |
| `oidc` | `PUBLIC_URL`, `OIDC_ISSUER` с HTTPS, `OIDC_CLIENT_ID`, `OIDC_CLIENT_SECRET` |
| `none` | Вход без учётной записи; для административного доступа нужен отдельный `ADMIN_TOKEN` от 32 символов |

Для OIDC зарегистрируйте callback `https://farm.example.com/api/oidc/callback`. Администраторов LDAP/OIDC перечислите в `ADMIN_SUBJECTS` через запятую: LDAP DN, OIDC subject или имя пользователя. Новые пользователи, которых нет в списке, получают обычную роль. Затем роль можно назначить через интерфейс; повторный вход сохраняет назначение.

Для обычной рабочей установки выберите `local`, `ldap` или `oidc`.

## Резервные копии и перенос

Сохраняйте базу PostgreSQL, том библиотеки приложений `app_store` и том образов `registry_data` как один комплект. Конфигурацию `.env`, сертификаты и `SECRETS_KEY` храните отдельно в менеджере секретов. Значения переменных контейнера из профилей в базе зашифрованы: на другом стенде они читаются только с тем же `SECRETS_KEY`. Поэтому ключ храните отдельно (менеджер секретов), но не теряйте. Если `SECRETS_KEY` не задан, ключ лежит в таблице `app_secrets` и переезжает вместе с базой.

### Согласованная копия

В окно обслуживания выполните из каталога установки:

```bash
bash scripts/backup-farm.sh /secure/backups
# Для нестандартного compose передайте его параметры после каталога:
# bash scripts/backup-farm.sh /secure/backups --env-file /opt/device-farm/secrets/app.env -f deploy/homelab/compose.yaml
```

Для копирования нужны уже созданные контейнеры `server` и `registry`, а также `docker`, `tar`, `gzip` и `sha256sum` на машине запуска. Архивы читаются из существующих томов в режиме только чтения; Docker-логирование архивного потока отключено. Служебные контейнеры работают без сети, с лимитами 1 CPU и 256 МиБ RAM.

На время копирования скрипт останавливает `web`, `server`, `registry`, делает `pg_dump`, архивы обоих томов и контрольные суммы, затем возвращает запущенные сервисы. Работающие на агентах контейнеры Android не удаляются; панель и новые команды недоступны на время копирования. При ошибке копирования сервисы также возвращаются, а неполный комплект нельзя считать бэкапом. Скрипт не копирует `.env` и не печатает секреты.

Проверьте восстановление **в новой пустой установке**, с той же версией схемы БД и тем же ключом. Запустите только PostgreSQL, восстановите дамп и тома, затем остальные сервисы. Перед `pg_restore` дождитесь здорового состояния PostgreSQL (`docker compose ps`); не запускайте сервер, пока пустая БД не восстановлена. Перезапись существующих томов не является безопасным способом тестирования бэкапа:

```bash
cd /secure/backups/farm-YYYYMMDDTHHMMSSZ
sha256sum --check SHA256SUMS
# Далее в каталоге новой установки; BACKUP — абсолютный путь к проверенному комплекту.
cd /path/to/new-installation
BACKUP=/secure/backups/farm-YYYYMMDDTHHMMSSZ
docker compose up -d postgres
docker compose exec -T postgres sh -ec 'pg_restore -U "$POSTGRES_USER" -d "$POSTGRES_DB" --exit-on-error' < "$BACKUP/postgres.dump"
docker compose run --rm --no-deps -T --entrypoint tar registry -C /var/lib/registry -xzf - < "$BACKUP/registry-data.tar.gz"
docker compose run --rm --no-deps -T --entrypoint sh server -ec 'tar -C "${APP_STORE_DIR:-/data/apps}" -xzf -' < "$BACKUP/app-store.tar.gz"
docker compose up -d
```

Проверьте вход, APK, `/v2/` (401 без авторизации), pull закреплённого digest и запуск сессии. Отдельно сохраняйте ключи агента и `agent_image_builds` на каждом узле. Не храните незашифрованные бэкапы в публичном bucket.

### Вынести существующий ключ из базы

**Нельзя просто задать новый `SECRETS_KEY` поверх старых данных.** Ключ из `app_secrets` и строка `SECRETS_KEY` преобразуются по-разному. Новая случайная строка без миграции лишит доступа к переменным профилей и паролю внешнего registry.

1. Схема БД должна содержать миграции текущей версии сервера. Сделайте согласованный бэкап. Остановите все экземпляры `server`, включая реплики.
2. Сохраните новый случайный `SECRETS_KEY` (от 32 символов) в защищённом `.env`. Если прежде использовался ключ из `.env`, передайте его отдельно как `PREVIOUS_SECRETS_KEY` в защищённом файле окружения одноразового контейнера. Для ключа из базы эта переменная не нужна.
3. Выполните офлайн-миграцию на **новом собранном образе** сервера:

```bash
docker compose stop server
docker compose build server
docker compose run --rm --no-deps -e RDF_SERVER_STOPPED=1 server node dist/migrate-secrets-key.js
docker compose up -d server
```

Миграция одной транзакцией перешифровывает переменные всех профилей и пароль registry, затем удаляет старый ключ из базы. Значения не выводятся. При ошибке транзакция откатывается: верните прежнюю конфигурацию до запуска сервера. После успеха удалите `PREVIOUS_SECRETS_KEY` из временного окружения; старые бэкапы требуют прежний ключ. Повторять миграцию с уже удалённым старым ключом не нужно.

Профили можно переносить без базы: **Администрирование → Профили устройств → Экспорт** даёт JSON без значений переменных (на их месте `null`), а **Импорт JSON** на новом стенде создаёт профили выключенными. Значения переменных введите заново или добавьте в файл перед импортом.

## Обновление и журналы

В каталоге установленного проекта:

```bash
git pull --ff-only origin main
docker compose up -d --build server web
docker compose ps
```

Обновление пересоздаёт сервер и веб-интерфейс; открытые соединения переподключатся. Для полноценной проверки используйте `/health` из контейнера, как в быстром запуске выше. Обновление агента выполняется [отдельно](agent.md).

В веб-интерфейсе администратор может открыть **Журнал → Лог приложения**: обычный текстовый поток вывода API-сервера с поиском, фильтром уровня, паузой, копированием и скачиванием `.log`. Новые строки приходят через SSE; после краткого обрыва соединения пропущенные строки догружаются. Буфер содержит последние 2000 сообщений текущего запуска (до 4096 символов в сообщении) и сбрасывается при перезапуске сервера. Для истории предыдущих запусков используйте журналы Docker. Журналы агента и Android в этот поток не входят.

Посмотреть последние сообщения:

```bash
docker compose logs --tail=100 server web postgres
```

Следить за журналом API:

```bash
docker compose logs --follow --tail=50 server
```

`Ctrl+C` завершает просмотр журнала, а не контейнер. Обычный `docker compose restart` не перечитывает `.env`; после изменения настроек используйте `docker compose up -d`.

PostgreSQL, библиотека APK и registry хранятся в именованных Docker volumes. Пересоздание контейнеров сохраняет эти данные; `docker compose down -v` удалит их.

Если панель не открывается, агент не появился или вход возвращает ошибку, начните с [решения частых проблем](../troubleshooting.md).

## Обновление и интерфейс

Перед обновлением сохраните PostgreSQL, `app_store`, `registry_data` и отдельную копию `SECRETS_KEY`. Миграции применяются автоматически до готовности API. Обновляйте только `server web registry`; агент обновляется отдельно. Для общего хоста не пересоздавайте остальные сервисы.

Пользователи отсортированы по имени; видны логин и дата регистрации. Администратор может создать пользователя, сбросить пароль (есть генератор) и удалить учётную запись. Удаление отзывает доступ и ожидающие заявки, сохраняет историю; активные сессии нужно сначала завершить. Удалённая LDAP/OIDC-учётная запись не восстанавливается следующим входом.

Keycloak/OIDC и LDAP/LDAPS задаются настройками `.env`. Выбирается один `AUTH_MODE`; начальные роли новых учётных записей задаются `ADMIN_SUBJECTS`, дальнейшее назначение выполняется в разделе «Пользователи». [Создание ролей и настройка прав](../guides/roles.md); синхронизации групп нет. Настройки и callback OIDC приведены выше.
