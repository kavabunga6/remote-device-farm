# Интеграции и автотесты

[Все руководства](../README.md) · [API и команды CLI](../api/README.md)

Один запуск выглядит так: ферма выделяет устройство → CLI подключает ADB → ваш инструмент выполняет тесты → CLI освобождает устройство. Тесты работают на вашем компьютере или CI-агенте.

## Быстро проверить подключение

Нужны Bash, `curl`, `jq`, GNU `timeout` (CLI также распознаёт имя `gtimeout`), Android Platform Tools (`adb`) и доступ к HTTPS фермы и ADB-портам узла. Для CI используйте Linux-агент с отдельным ADB-окружением. На компьютере разработчика команды также можно выполнять в Git Bash; окружение Android SDK и ADB должно быть настроено заранее.

1. Создайте личный API-токен в аккаунте фермы.
2. Добавьте публичный ADB-ключ этого компьютера в аккаунт. Парная закрытая часть должна быть доступна локальному ADB-серверу.
3. Выберите ID готового профиля в ферме. В примерах используется `android-30`; на вашей установке ID может отличаться.
4. Из корня репозитория выполните:

```bash
export RDF_URL='https://farm.example.com'
export RDF_PROFILE='android-30'
export RDF_ADB_KEY_ID='33333333-3333-4333-8333-333333333333'
read -rsp 'API-токен: ' RDF_TOKEN
printf '\n'
export RDF_TOKEN

bash scripts/rdf.sh run -- bash -c '
  set -euo pipefail
  env -u RDF_TOKEN adb -s "$ANDROID_SERIAL" shell getprop ro.build.version.release
'
```

Замените адрес и ID своими значениями. Команда дождётся устройства, выведет версию Android и освободит слот. Сообщение `request released; cleanup confirmed` подтверждает очистку. Затем выберите руководство своего инструмента из таблицы выше.

Если переносите CLI в репозиторий приложения, сохраните его как `ci/rdf.sh`. Копируйте файлы из одного зафиксированного коммита фермы: это позволит воспроизвести запуск и обновить пример вместе с документацией. Сохраняйте окончания строк LF. Значения таймаутов задавайте положительными целыми числами без ведущих нулей, например `60`, а не `060`.

## Как запускать свои тесты

Оборачивайте команду тестов в `rdf.sh run`. Она получает `ANDROID_SERIAL`, `RDF_SESSION` и `RDF_STATE_FILE`. Указывайте устройство явно, чтобы инструмент не выбрал другой подключённый телефон.

```bash
bash ci/rdf.sh run -- bash ci/android-tests.sh
```

Сборку APK и установку зависимостей выполняйте **до** этой команды: устройство не будет занято во время сборки. Журналы и скриншоты собирайте внутри `android-tests.sh`, пока сессия доступна. После завершения команды CLI освобождает устройство, поэтому получить новые артефакты уже нельзя.

| Задача | Где описано |
| --- | --- |
| Установить APK и выполнить Maestro flow | [Maestro](maestro.md#первый-запуск) |
| Использовать Appium с `appium:udid` | [Appium](appium.md#подключить-свои-тесты) |
| Настроить переменные, сроки аренды и ожидания | [Справочник CLI](../api/README.md#одна-команда-с-автоматическим-освобождением) |
| Сохранить JUnit, logcat и скриншоты | Раздел об артефактах в руководстве выбранной CI |

Gradle-задачи в примерах рассчитаны на модуль `app` и вариант `debug`. Укажите свои задачи и пути отчётов. Для конфигурации `deviceFarm { ... }` подключите [Gradle-плагин](gradle.md).

## Параметры устройства во всех интеграциях

Перед запуском общего CLI задайте дополнительные настройки:

```bash
export RDF_DISK_GB=16
export RDF_SD_CARD_MB=1024
export RDF_EMULATOR_PARAMS='-no-snapshot -no-boot-anim'
bash ci/rdf.sh run -- bash ci/android-tests.sh
```

Это внутренняя память Android, отдельная SD-карта и разрешённые аргументы Android Emulator. В GitHub/GitLab и Jenkins они задаются обычными переменными задания, в TeamCity — параметрами `env.RDF_DISK_GB`, `env.RDF_SD_CARD_MB`, `env.RDF_EMULATOR_PARAMS`. Maestro и Appium получают уже запущенное устройство с этими настройками. Интеграции используют один контракт; отдельного списка настроек для каждого инструмента нет.

Не заданная переменная оставляет значение профиля. Размеры ограничены максимумами `diskMaxGb` и `sdcardMaxGb`, которые задаёт администратор. `RDF_SD_CARD_MB=0` выключает SD-карту; `RDF_EMULATOR_PARAMS=''` удаляет дополнительные аргументы профиля. CPU и оперативная память берутся из профиля. Администратор может запросить `RDF_PRIVILEGED=1`, если этот режим разрешён в настройке агента; по умолчанию он выключен. [Размеры, ограничения и разрешённые аргументы](../api/README.md#память-устройства-sd-карта-и-аргументы-запуска).

## Отмена, ошибки и повторное освобождение

При нормальном завершении, ошибке теста и сигналах отмены CLI пытается освободить устройство и ждёт подтверждения. Если процесс CI потерян, аренда перестаёт продлеваться: сервер запросит очистку. При недоступном агенте слот остаётся занятым до подтверждения очистки.

Если освобождение не подтвердилось, сохраните файл состояния, путь которого напечатан в журнале. Передайте прежний адрес фермы, токен того же аккаунта и этот файл:

```bash
export RDF_STATE_FILE="$PWD/session.json"
bash ci/rdf.sh release 180
```

Не запускайте новую заявку поверх сохранённого состояния. Не удаляйте блокировку `.lock`, пока не убедились, что прежний процесс остановлен. [Подробное восстановление](../api/README.md#если-запрос-или-освобождение-прервались).

| Симптом | Что проверить |
| --- | --- |
| Очередь не заканчивается | Есть ли совместимый узел, свободный слот и доступный профиль; увеличьте срок ожидания только если это ожидаемая очередь |
| `unauthorized` или таймаут ADB | Выбран ли ID нужного публичного ключа и использует ли ADB парный закрытый ключ |
| CLI видит устройство, а тесты нет | Передан ли `ANDROID_SERIAL`; используют ли CLI и тесты один ADB-сервер |
| Тест завершился, job упал | Проверьте сообщения очистки: ошибка освобождения тоже делает задание неуспешным |
| JUnit отсутствует | Могла упасть сборка или запуск устройства до тестов; откройте журнал CI и `rdf-run.log`, если он собирается |

## Секреты и параллельные задания

- Храните API-токен в секретах CI. Не включайте `set -x` и не печатайте окружение. Запускайте с токеном только доверенный код: дочерний скрипт может обращаться к API, например для сбора logcat.
- Закрытый ADB-ключ храните только на компьютере тестов. Не добавляйте его в Git или артефакты. Выбор `RDF_ADB_KEY_ID` не меняет ключ аккаунта по умолчанию.
- Используйте отдельные ADB-окружения, файлы состояния и каталоги артефактов для параллельных запусков. Разные файлы состояния не изолируют ADB. Не вызывайте общий `adb kill-server` из задания.
- Доступ к отчётам и скриншотам выдавайте тем же людям, которым доступна тестовая сессия: в них могут быть данные приложения.

## Что требуется перед выпуском интеграции

Для каждой заявленной CI-системы нужен прогон в самой системе: успешный тест, падение теста, отмена во время очереди и тестов, а также потеря runner. Нужно подтвердить сохранение доступных артефактов, исходный код ошибки и освобождение слота. Отдельно проверьте восстановление по файлу состояния после недоступности API.

У Appium [закреплены исправленные зависимости драйвера](appium.md#закрепление-зависимостей-и-аудит); требуется выполнить живой прогон smoke-теста с установкой UiAutomator2, скриншотом и удалением сессии. Gradle-плагин требует живого прогона с Android Gradle Plugin. Расширение IDE пока отсутствует.

### Локальная проверка

Из корня репозитория запустите общую проверку на Node.js 24. В `PATH` должны быть Bash, curl, jq и GNU timeout (на macOS допустим `gtimeout`). Она проверяет синтаксис примеров, ссылки документации и поведение CLI и адаптеров:

```bash
node scripts/check-integrations.mjs
```

Groovy-тесты Jenkins и Gradle TestKit запускаются на JDK 17+:

```bash
integrations/gradle/gradlew -p integrations/gradle check
```

Зависимости Appium проверяются отдельно:

```bash
cd examples/appium
npm ci
npm audit --audit-level=high
```

Проверяйте закреплённое дерево зависимостей Appium перед установкой и обновлением.

Локальные проверки находятся в [`scripts/test`](../../scripts/test/), а запуск проверок репозитория — в [CI workflow](../../.github/workflows/ci.yml). Эти проверки дополняют живые прогоны, но не заменяют их. До выполнения оставшихся проверок весь набор интеграций не заявляется готовым релизом.
