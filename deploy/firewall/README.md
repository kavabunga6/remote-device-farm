# Сетевая изоляция эмуляторов

По умолчанию эмулятор в сессии получает «выход наружу» через обычный Docker bridge. Без фильтра из него
можно достучаться до домашней или офисной сети, до самого узла фермы и до его служб. Скрипт ниже закрывает это.

## Что делает

Агент называет bridge выходной сети каждой сессии `rdfe<11 hex>`, а управляющей — `rdfm<11 hex>`.
Скрипт `rdf-egress-firewall.sh` фильтрует обе сети в цепочке `DOCKER-USER`:

- интернет доступен;
- частные диапазоны (`10/8`, `172.16/12`, `192.168/16`, `169.254/16`, `100.64/10`), loopback и multicast закрыты;
- другие Docker-сети узла и `docker0` закрыты безусловно, даже при широком `ALLOW_DEST`;
- запросы к самому узлу (SSH, агент, база данных) отбрасываются в цепочке `INPUT`;
- уже установленные соединения к запрещённым адресам тоже блокируются при включении защиты;
- в управляющей сети соединение может открыть агент; контейнер может отвечать по этому соединению, но не открывать своё к агенту. Правило распространяется на TCP и UDP.

Управляющая сеть остаётся внутренней. Агент получает отдельный MAC-адрес из `agent/src/network-policy.json`;
ответы контейнера допускаются только в обратном направлении соединения. Сам по себе статус Docker `internal`
не закрывает доступ между участниками одного bridge.

В новых управляющих сетях Docker также выключает inter-container communication (`enable_icc=false`).
При включённом bridge netfilter новые соединения запрещены ещё до применения пользовательской политики.
Поэтому firewall нужно установить до запуска сессий: только он разрешает агенту подключаться к устройству.

## Установка на узле фермы

Команды выполняются из каталога `deploy/firewall` на Linux-узле.

```sh
sudo install -m 0755 rdf-egress-firewall.sh /usr/local/sbin/
sudo install -m 0644 ../../agent/src/network-policy.json /usr/local/sbin/network-policy.json
sudo install -m 0644 rdf-egress-firewall.service /etc/systemd/system/
printf 'br_netfilter\n' | sudo tee /etc/modules-load.d/rdf-bridge.conf
printf 'net.bridge.bridge-nf-call-iptables = 1\n' | sudo tee /etc/sysctl.d/90-rdf-bridge.conf
sudo modprobe br_netfilter
sudo sysctl -p /etc/sysctl.d/90-rdf-bridge.conf
sudo tee /etc/rdf-firewall.conf >/dev/null <<'CONF'
# Частные DNS-серверы, к которым эмулятору разрешён прямой доступ.
# Укажите IP отдельного резолвера в LAN; DNS самого узла блокируется цепочкой INPUT.
ALLOW_DNS="192.0.2.53"
# внутренние тестовые стенды, которые эмуляторам разрешено видеть
ALLOW_DEST=""
CONF
sudo systemctl daemon-reload
sudo systemctl enable --now rdf-egress-firewall
sudo rdf-egress-firewall.sh status
```

Unit запускается вместе с Docker и повторно применяет политику при его перезапуске. После обновления
unit повторите `sudo systemctl daemon-reload` и `sudo systemctl enable --now rdf-egress-firewall`,
чтобы обновить зависимости автозапуска.

Установите firewall и ресурс политики до предоставления доступа недоверенным пользователям. Без включённого
`bridge-nf-call-iptables` или рабочего Docker hook скрипт откажется применять правила. Используйте файл политики
из той же версии, что и агент; его копия внутри агента включается в Docker-образ и Linux-архив.

При обновлении завершите старые сессии и создайте их заново. Старые управляющие сети без префикса `rdfm`,
без запрета ICC или с прежним MAC агента не подходят для этой политики; агент отказывается использовать их повторно.

## Проверка

Запустите сессию и выполните в консоли устройства:

```sh
ping -c1 8.8.8.8        # должен отвечать
ping -c1 <IP-узла>      # не должен
ping -c1 192.0.2.53    # не должен (если адрес не разрешён в ALLOW_DEST)
```

В выводе `status` растут счётчики пакетов правил DROP. Проверьте также TCP-соединение к IP узла и
соседнему адресу LAN: один только ICMP не доказывает изоляцию. Если DNS из эмулятора идёт прямо к частному
резолверу, добавьте его адрес в `ALLOW_DNS`. Встроенный DNS Docker (`127.0.0.11`) может пересылать запросы
через сам Docker daemon и не подчиняется правилу `ALLOW_DNS`; проверьте разрешение имён отдельно при
включённом и отключённом выходе в сеть.

`systemctl restart rdf-egress-firewall` обновляет правила без окна открытого доступа. Остановка unit оставляет
их активными. Для явного удаления этих правил после завершения всех сессий используйте
`sudo rdf-egress-firewall.sh remove`. Это не включает Docker ICC: без разрешающей политики новые управляющие
соединения остаются запрещены при включённом bridge netfilter.

## Ограничения

- Скрипт написан для `iptables`; для чистого nftables нужны эквивалентные правила в `DOCKER-USER`.
- IPv6 в сетях сессий выключен, отдельных правил для него нет.
- В изолированной Linux VM с Docker 29.9.3 проверены запрет новых management-соединений без пользовательской политики, TCP/UDP после её применения, двусторонняя передача по соединениям агента, блокировка ранее открытого контейнером TCP-потока, повторное применение и восстановление после ошибки обновления. Контролируемые службы узла, LAN, metadata и соседнего арендатора блокировались; разрешённая внешняя цель оставалась доступной. Проверены широкий `ALLOW_DEST`, выключение и включение выхода в сеть, попытки root открыть raw-сокет и сменить MAC. Это проверка контейнерной границы с синтетическими сетевыми службами, без запуска Android/KVM/GPU; периметр рабочего узла требует отдельной проверки.
- Идентичность endpoint защищается стандартными ограничениями контейнера: `CapDrop=ALL`, `no-new-privileges` и отсутствие privileged-режима. Выдача `CAP_NET_RAW`, `CAP_NET_ADMIN` или privileged-режима недоверенному контейнеру нарушает эту границу. Выход через уязвимости Android, KVM, Docker или GPU этой проверкой не исключается.

### Совместимость Docker

MAC проверяется внутри I/O-агента после каждого подключения. На Docker API до 1.54 поле `MacAddress` при network connect может игнорироваться. Поставляемый агент содержит `iproute2`: управляющий процесс исправляет адрес только нового интерфейса через кратковременный привилегированный exec в сетевом пространстве I/O-агента. Права постоянных процессов и эмулятора не расширяются. Ошибка проверки прерывает запуск; правила firewall не ослабляются. Подробности — в [инструкции агента](../../docs/deployment/agent.md#совместимость-управляющей-сети).
